Read-only API

Method: GET · Response: JSON · API version: 1.0

https://prhhlvdoplavakbgcbes.supabase.co/functions/v1/reports-api-v1

Send the integration key in the x-api-key request header. This is a dedicated key, not a Supabase service-role key and not a user password. Its SHA-256 hash is stored server-side.

Scope: Austin’s submitted reports only, selected using his fixed submitter ID. The caller cannot pass another user or team to broaden access. Austin’s reports span teams, so this is deliberately not limited to just the team named “Lone Oak.” Please confirm that author-only scope matches your intended dashboard.

Example request

Replace YOUR_INTEGRATION_KEY locally. Do not put the real key in a public webpage, Git repository, or browser-side dashboard bundle.

curl "https://prhhlvdoplavakbgcbes.supabase.co/functions/v1/reports-api-v1?submitted_since=2026-10-01T00:00:00Z&limit=100" -H "x-api-key: YOUR_INTEGRATION_KEY"

Query parameters

submitted_since or since
ISO-8601 timestamp. Returns reports whose creation/submission timestamp is greater than or equal to this value. Results sort oldest first.
changed_since
Filters on the new updated_at field and sorts by it. If combined with submitted_since, both filters apply. Use this alone when you want edits to older reports.
limit
Default 100, maximum 200 reports per response. At least one timestamp filter is required.

Response envelope

{
  "api_version": "1.0",
  "generated_at": "ISO-8601 timestamp",
  "integration": "Will Correll dashboard v1",
  "filters": {
    "submitted_since": "ISO-8601 timestamp or null",
    "changed_since": null,
    "submitter_id": "Austin's fixed user ID"
  },
  "count": 2,
  "has_more": true,
  "next_since": "last returned report's filter timestamp",
  "reports": [ /* report objects described below */ ]
}

Envelope above is a structural illustration, not a literal JSON fixture. Actual samples below are valid JSON.

Sync limitation to resolve together: filters are inclusive; deduplicate/upsert by id. The current next_since is only a timestamp, not a unique cursor. Tied timestamps can repeat pages or prevent progress. A stable timestamp-plus-ID cursor is still needed before a full backfill. Do not advance by an arbitrary millisecond, since that can skip reports.

Errors: 401 for a missing/invalid/expired key; 400 for missing or invalid timestamp filters; 405 for a non-GET request; 500 for a server-side failure. Keep the integration server-side. Key revocation is supported through the credential’s active flag; rotation/handoff remains an administrative step.

Field map & data meanings

API v1 report object → Supabase source
API fieldSource / meaning
idsubmissions.id · stable UUID; use as the upsert key.
submitted_atcreated_at · stored row creation time, used as submission time by the current direct-submit flow. Not a separately tracked status-transition timestamp.
last_changed_atupdated_at · newly added, updated on report-row edits. Old edit times cannot be reconstructed; the migration initialized existing rows at migration time. Product-only edits do not yet touch the parent timestamp.
submitted_byObject: id, display_name, email. Comes from the author’s current Auth profile, not a historical profile snapshot.
storeObject: name ← store_site; number ← store_number; chain ← store_chain; address ← store_location. Missing data remains null; chain is not guessed from store name.
report_datedate · calendar date, YYYY-MM-DD; not a UTC instant.
brandbrand · surrounding whitespace trimmed by API; legacy spelling/case is not silently rewritten.
location_in_storelocation · aisle, bunker, shelf, or other placement.
conditionsconditions · existing free text.
priceObject: amount is decimal USD, currency: "USD", stored_in_cents: false, and amount_cents is derived. Example: 2.99 dollars → 299 cents. Confirm USD assumption for all reports.
shelf_spaceshelf_space · text such as “3 shelves”; no numeric unit is inferred.
faceson_shelf converted to a number when valid. Historical input is free-form, so surprising values need review rather than silent correction.
tags, notesString array and free-text notes respectively. Existing quantities/dates inside notes are preserved, not automatically parsed.
prioritypriority_level · 1 urgent/red, 2 yellow, 3 OK/green; can be null for legacy data.
productsArray from submission_products: id, product, numeric/null quantity, YYYY-MM-DD/null expiry_date. Empty for older reports.
photosUp to six objects: slot, path, url, expires_at. Signed URLs last one hour. Refresh via the API; do not treat URLs as permanent IDs. Legacy URL-only photos are not yet recovered by this version.

Nullable fields should stay null, not become invented values or zero. API strings are trimmed; the raw database samples below preserve their original formatting.

Keeping your connection stable

Proposed v1 compatibility policy: keep existing endpoint and field names stable. Add optional fields without removing existing ones. Changes to names, types, units, timestamp meanings, or access scope require advance discussion, updated sample data, and a versioned migration plan.

If a breaking change becomes necessary, agree on a new reports-api-v2 contract and a transition window before retiring v1. Keep a changelog and notify you before deployment. No existing submission fields have been renamed as part of this work.

This is the working agreement proposed for the handoff, not an automated notification service or an already-agreed deprecation deadline.
