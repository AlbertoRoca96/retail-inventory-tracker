What actually limits the current app

  • Data layout: reports currently have six fixed photo path/URL slots. The uploader, API, spreadsheet, detail view, and PDF also have six-photo assumptions. Raising a picker limit alone would risk silently dropping photos.
  • Upload: native selection uses JPEG quality settings, but the shared upload helper does not apply a consistent resize/compression budget. Web uploads can retain full-resolution files.
  • PDF memory: native PDF export resizes inline images to 1,400 pixels wide, but still assembles multiple images in HTML. Base64 adds roughly one-third to encoded bytes, and decoded image memory is much larger. Twenty photos need testing on real iPhones, not just a faster server.
  • Time & reliability: mobile bandwidth, per-photo retry, progress indication, and recoverable uploads matter more than raw database capacity. The deployed legacy pipeline can omit assets beyond six; the local uploader now rejects more than six instead of silently truncating. Retain this clear limit until all consumers support more.
Privacy finding: the submissions storage bucket is currently public. Expiring signed URLs do not enforce private access while public URLs remain available. Do not describe the photos as key-protected end to end yet. A separate privacy migration must audit current consumers, replace public links, test authenticated/signed reads, and then switch the bucket to private.

Recommended rollout

  1. Finish the structured report integration first; keep the six-photo supported limit for this release.
  2. Add a submission_photos child table with ordered photo rows, retain legacy six-slot compatibility, and update every reader/exporter.
  3. Normalize uploads with a tested size/quality target—start by evaluating 1,600–2,000-pixel long-edge JPEGs and roughly 0.3–0.7 MB/photo, checking label/expiry readability before accepting that target.
  4. Pilot 12 photos with upload progress/retries and paginated PDF photo pages. Keep higher-quality originals only if the business needs them; budget both variants if retained.
  5. Approve 20 only after real-device PDF, offline/retry, image clarity, and quota checks. No claim that twenty-photo support is implemented today.

Bottom line for Austin: twenty photos is not inherently impossible and does not automatically require a larger plan. The current six-slot implementation and phone-side PDF handling need engineering work. Measure usage and compress sensibly before buying capacity.
